## Active Focus

Prepare the next serious method while keeping the workflow simple:

1. Keep the active Colab notebooks Drive-backed and directly runnable.
2. Use probe-on-log, generated-eval-on-save, and final generated eval to compare checkpoints and final adapters.
3. Build Kaggle submissions locally from Colab run bundles.
4. Start the next procedural-supervision direction as solver-guided STaR: generate, verify, filter, and train on compact reasoning traces from our own pipeline rather than copying public trajectory notebooks or datasets.
5. Treat free-form base-model vLLM rejection sampling for cipher/bit as tested and rejected as-is. The next data-building step should not be more open-ended sampling.
6. For cipher, use an answer-conditioned STaR-style rationale probe next: give the training question and the known `gold_answer`, ask the frozen model to produce a short mechanical rationale that reaches that answer, then filter for trace quality before any SFT. This is allowed for training rows and is different from RFT because the answer is supplied after open RS failed.
7. Keep constrained solver/candidate-list or multiple-choice cipher selection as the fallback if answer-conditioned rationales are low-quality, leaky, or still too long. Do not ask the model to free-form solve long cipher traces again.
8. For bit manipulation, prefer programmatic candidate-rule search or an expanded DSL verifier over model-written rule explanations. The two accepted exp14 bit traces are too few and too weak to train on.
9. Keep the other families on the existing deterministic template or boxed-control path for now. Gravity, unit conversion, and numeral templates already gave useful procedural signal; equation remains boxed-only until a real verifier exists, not because it is solved.
10. Use `doc/POST_TRAINING_METHOD_LADDER.md` as the stop-and-escalate reference when a method class plateaus: SFT -> rejection sampling + SFT -> preference optimization/DPO -> online RL/RLVR, with small diagnostic runs before expensive training.
11. Build `eval_v2` before trusting a new family-general conclusion: larger, family-balanced, grouped where feasible, and reporting hard-family accuracy excluding numeral.

Current collaboration loop:

1. Brainstorm candidate ideas together, with critique focused on simple non-trivial methods that can plausibly move the score. Be explicit about what was actually tested versus what only sounds similar; do not treat template trace SFT as proof for or against true high-quality CoT annotation SFT.
2. Choose one idea before implementation; avoid mixing unrelated knobs unless there is a deliberate reason.
3. Implement the selected idea as a notebook-first experiment with Occam's razor.
4. Run it in Colab, then copy/download the run bundle and diagnostics locally.
5. Build the strict Kaggle `submission.zip` locally from the run bundle adapter files.
6. Update the experiment dashboard, checklist, memory, and decision log with the evidence.
7. Iterate until the public score reaches at least `0.7` or the evidence forces a better target strategy.

Originality constraint: all outside research is allowed as literature, tools, and inspiration, including papers, open-source code, Reddit/Medium/Substack posts, YouTube talks, other-domain competition ideas, and reasoning-challenge methods that are not from this exact Nemotron Kaggle challenge. Do not inspect or copy another active Nemotron challenge competitor's high-scoring notebook, GitHub repo, trajectory dataset, or submission path as the main method unless explicitly approved. The goal is to discover this project's own trajectory and learn the research process.
